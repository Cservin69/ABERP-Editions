# ADR-0110 D3 — the FROZEN money-path durable-ack census.
#
# One line per production call site of `Handle::durable_ack()`: the ack
# boundaries where an operator is told a money-path write succeeded, and where
# that write must therefore already be in the power-loss durable set (ADR-0110
# R1). `tools/cut_gate_durable_ack.sh` holds this set closed in BOTH directions:
#
#   * a site that loses its `durable_ack()` call goes red (the regression that
#     actually matters — a refactor silently un-durables invoicing);
#   * a file whose call count no longer EQUALS the number of lines it has here
#     goes red (CHECK D3-A is a per-file equality, not `>= 1`). Several files
#     below carry three or four lines — one per ack BOUNDARY — and without the
#     equality an ack could be moved from one censused file to another with the
#     whole-tree total D3-B checks left intact. Adding or removing a boundary
#     means editing this file, deliberately, in the same PR;
#   * a NEW `durable_ack()` call site that is not listed here goes red, so
#     growth is a deliberate, reviewed edit of this file and not a drive-by;
#   * a site that KEEPS the call but SWALLOWS its error goes red (CHECK D3-C).
#     Added after the PR #59 adversarial found that rewriting
#     `db.durable_ack().context(..)?` as
#     `if let Err(e) = db.durable_ack() { warn!(..) }` — the exact ADR-0110 R3 /
#     CLAUDE.md rule-11 downgrade — left the gate green. A present-but-ignored
#     ack is the 2026-08-08 posture with a log line.
#
# Format: <path>\t<function>\t<what the operator was told>
# Lines starting with '#' and blank lines are ignored.
#
# Adding a site: add the call, add the line here, and say in the PR why that
# ack is a money path. Removing one: it must be because the ack itself is gone.
#
# NOT listed, deliberately:
#   * `incoming_invoices::change_status`'s early `from_parsed == to_status`
#     return — it writes nothing, so there is nothing to make durable.
#   * every non-money write (quotes, inventory, MES, catalogue, email outbox).
#     ADR-0110 bounds the blast radius on purpose: fsyncing every write in the
#     system would put the cost on paths that do not carry the risk. The scope
#     came from ONE incident.
#
# DEFENSE DIVERGENCE (read before reasoning from the Portable ADR).
# On Portable the standing warning is "H4 — still unbuilt — is what would cover
# the rest". That is FALSE here and the sentence has been removed rather than
# carried over. Defense HAS a built, validated durable checkpoint
# (`aberp_snapshot::durable_checkpoint` / `live_durable_checkpoint`, driven from
# `aberp_db::Handle`'s debounced post-commit hook, crash-safe via a journaled
# `atomic_install`). There is no "H4" identifier anywhere in this tree.
#
# So the residual Defense carries after D3 is NARROWER than Portable's: a
# non-money write is covered by the debounced checkpoint within
# DEFAULT_MIN_CHECKPOINT_INTERVAL (60s) rather than not at all. D3 exists here
# to close the *window* on money paths (ack-time vs up-to-60s-later), not to
# substitute for a checkpoint that does not exist.

# ── D-22 (ADR-0114, 2026-08-26): the NAV money-submission CLI paths joined ────
#
# The census above was written when the ONLY `durable_ack` sites were the five
# issuance / payment boundaries. That was never the whole money surface: every
# NAV *submission* path — `submit-invoice`, `retry-submission`,
# `drain-submission-queue`, `drain-pending-retries`, `poll-ack`,
# `poll-annulment-ack`, `submit-annulment`, `observe-receiver-confirmation`,
# `recover-from-nav`, `mark-abandoned`, `request-technical-annulment` — also
# tells an operator a money-path write succeeded, and none of them claimed a
# flush. Two distinct shapes were open (ADR-0114 §2):
#
#   * eight commands did `Ledger::open` -> `append` -> `sync_mirror` on their
#     OWN `Connection`, so no flush ever ran: the audit MIRROR was explicitly
#     `fsync`ed and the DB was left to whatever DuckDB does with its WAL. That
#     is the ADR-0099 §R2.2 inversion — the 2026-08-08 loss shape — and it was
#     live on real NAV ÁFA filings. They are now Handle-routed;
#   * three (`submit_invoice`, `poll_ack`, `drain_pending_retries`) were
#     already Handle-routed, so the `WriteGuard` drop DID flush — but nothing
#     claimed the parked outcome, so a flush that FAILED printed
#     "submitted invoice …" anyway and left only a `tracing::error!`. That is
#     the rule-11 downgrade CHECK D3-C forbids, reached by omission instead of
#     by a `warn!`.
#
# The ack sits at the boundary of the WRITE it belongs to, not once per
# command: an Attempt-before-call row must be durable BEFORE the wire send (a
# power loss mid-flight otherwise leaves NAV holding a submission ABERP has no
# record of attempting), and the TX2 row must be durable BEFORE the operator is
# told the filing landed. Hence several lines per file.
#
# NOT joined, deliberately (ADR-0114 §5): the two `aberp-snapshot::recover`
# sites the D-22 backlog entry also names. They run at BOOT, before any Handle
# exists, on a PRIVATE staging file, and the mirror top-up at
# `build_and_validate` §5d is an INPUT to the ahead-snapshot self-certification
# gate — its result decides Recover vs Refuse, so it structurally cannot move
# after the install. Neither writes a money row. The install itself is durable
# (`fsync_file` -> `rename` -> `fsync_dir`), so the DB catches up within the
# same boot. Named as the residual rather than quietly dropped.
