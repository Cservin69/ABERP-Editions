# ADR-0099 R2 — FROZEN audit-WRITER provenance residual (cut-gate CHECK 10P).
#
# Format: <file>:<fname>  (line numbers dropped so a benign shift never churns
# it — cf. CHECK 10k). One line per RUNTIME fn that writes the audit ledger
# (table OR mirror) and whose connection provenance is NOT the shared
# `aberp_db::Handle` writer, as classified by
# tools/adr0099_audit_writer_scan.awk. Every entry below is a SANCTIONED
# non-shared writer with the reason it cannot fork the `aberp serve` writer.
#
# NOTE (ADR-0099 R2): this gate covers the SECOND-WRITER class. The seq-2508
# incident was NOT that class — it was a lost DB commit (R2.2). Kept because the
# second-writer class is real and recurred four times, not because it explains
# seq 2508.
#
# Anything NOT on this list that the scanner verdicts READ_CLONE, INDEP_OPENER
# or UNCLASSIFIED fails the build. Unlike CHECK 10M this is not a ban-list of
# known-bad names: the scanner fires on the WRITE and demands a provable
# provenance for it, so an unrecognised one is RED by default.
#
# ── SEPARATE-PROCESS CLI ONE-SHOTS ──────────────────────────────────────────
# `aberp <subcommand>` is a different process from `aberp serve`. It has no
# shared Handle to route through, and its writes cannot collide with the serve
# writer's in-process seq assignment (cross-process racing is backstopped by
# the hash chain, as it always has been — see AUDIT_APPEND_LOCK's docs).
apps/aberp/src/snapshot.rs:emit_reopen_cli
apps/aberp/src/tenant_registry.rs:emit_tenant_reopen
#
# ── PRE-HANDLE BOOT ─────────────────────────────────────────────────────────
# Runs BEFORE `open_tenant_handle` (apps/aberp/src/serve.rs) and before any
# daemon is spawned, so there is exactly one thread and no Handle to share.
#
# D-21 R2 (ADR-0119): `serve.rs:run` is NO LONGER allow-listed. Its one inline
# pre-Handle audit write — the boot mirror reconcile — was extracted into the
# named `boot_reconcile_audit_mirror`, allow-listed below. `run` is now RED for
# any audit write left in (or added to) its body, closing the "fork hidden in a
# 3,000-line fn" hole ADR-0099 §R2 named. Each allow-listed boot fn is pinned to
# exactly one caller (`run`, pre-Handle) by the CHECK 10N-style caller-set gate,
# so the exemption cannot rot into a wholesale one if a daemon later calls it.

# ── SANCTIONED CLI-ONLY RECONCILE SEAM ──────────────────────────────────────
# `take_snapshot_with(.., MirrorReconcile::OnExportConnection)` — the CLI arm
# only. In `aberp serve` the reconcile is hoisted to the caller and runs under

crates/aberp-snapshot/src/take.rs:take_snapshot_with
#
# ── SANCTIONED SERVE-IS-PROVEN-STOPPED SEAM (ADR-0116 D3.4 rev 2) ───────────
# `rebuild_mirror_for_restored_db` writes the FRESH `<db>.audit.log` for a
# database that `restore --in-place` has just installed. It is the strictest
# provenance in this file, not the weakest:
#
#   * it is reachable ONLY from `restore_in_place`, whose caller
#     (`aberp::snapshot::run_restore_in_place`) refuses to proceed unless
#     `ensure_serve_is_stopped` takes DuckDB's own EXCLUSIVE file lock — and
#     re-asserts it at the commit point, so a serve started during the
#     pre-flight cannot slip through. There is provably no other writer;
#   * it is a separate process from `aberp serve` with no shared Handle to
#     route through, the same reason `emit_reopen_cli` is listed above;
#   * it reaches `ensure_consistent_with_db` with NO mirror at the live path
#     (the preserve step moved it into the `.PRE-RESTORE-` unit), so it takes
#     the `Created` branch and writes `[1..=db_max_seq]` from the DB under the
#     mirror's own flock. It is the SAME entry point serve boot uses, so the
#     mirror it leaves is the one boot would have produced.
#
# It exists because leaving the pre-rollback mirror at the live path made
# `aberp serve` refuse to boot after every backwards in-place restore
# (`MirrorDivergedFromDb` -> `RefuseFatal`).
crates/aberp-snapshot/src/take.rs:rebuild_mirror_for_restored_db

#
# ── LEDGER_LOCKED — FROZEN (D-21 R3, ADR-0119) ──────────────────────────────
# D-21 R3 promoted the scanner's `LEDGER_LOCKED` verdict from ACCEPTED to
# FAILING-UNLESS-FROZEN (CHECK 10P-2), turning ADR-0105's classification into a
# proof: the genuine in-process Domain-B writers (the audit-ledger SESSION api)
# were migrated onto `Handle::with_ledger` in ADR-0105, so the in-process
# direct-`Ledger::append` surface is EMPTY. A real `Ledger::append` always
# carries connection provenance the scanner traces — a read clone -> READ_CLONE,
# an independent open -> INDEP_OPENER, `db.write()` -> HANDLE_WRITE, inside
# `with_ledger` -> WITH_LEDGER. `LEDGER_LOCKED` is reached ONLY when `.append(`
# fires with NO traceable connection provenance: i.e. an audit append whose
# safety the scanner cannot prove (a genuine new Domain-B fork risk), OR the
# scanner's broad `.append(` matcher firing on a NON-`Ledger` `.append`.
#
# EVERY entry below is the latter — a scanner false-positive, verified to write
# NO aberp `Ledger`:
#   * mes_manager:boot_from_toml     — `handles.append(&mut spawned)` (Vec::append)
#   * export_invoice_bundle:append_bytes — `builder.append(&header, bytes)` (tar)
#   * aberp-portal-agent:*           — `self.audit.append(&Event…)`, the portal
#     agent's OWN append-only JSONL audit log (ADR-0115 §6.5), in a SEPARATE
#     binary (`aberp-portal-agent`), never the aberp tenant Ledger.
# Frozen may-only-shrink: a NEW LEDGER_LOCKED — a real `Ledger::append` with
# unprovable provenance, or a new non-ledger `.append` — reds until reviewed and
# either routed through `with_ledger`/the Handle writer (if a real ledger write)
# or added here (if another verified false-positive).
